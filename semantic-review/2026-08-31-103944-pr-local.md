# Single-CAS atomic commerce paths for orders, bookings, and BiLED with locked-down Firebase writes

This change moves every stock- and slot-mutating operation behind a single compare-and-set (CAS) commit so a crash can no longer leave "stock decremented but no order" or "slot held but no booking" states. On the edge, the Cloudflare Worker gains `/booking`, `/biled-order`, and `/admin/catalog-write` endpoints that write with a service-account token, and `database.rules.json` flips every catalog/order/booking/counter node to `.write: false` so browsers can no longer write directly. In Python, `create_order`, `create_order_from_items`, `import_external_order`, and `restore_shop_order` now run inside a dedicated `BEGIN IMMEDIATE` transaction with per-row stock reservation, size-aware stock, request fingerprints for idempotency, and a `stock_reserved` flag that keeps cancel-time restock exactly-once. Booking reconciliation was rewritten to treat SQLite as the single source of truth for the `slots` tree.

Watch for:
- **(confirmed)** `push_all_booking_slots` now full-PUTs the entire `slots` tree from SQLite active bookings only, but Worker/Mini-App bookings never reach SQLite — every restart or `/firebase` wipes their slot holds and re-opens the times for double-booking.
- **(confirmed)** All catalog writes and ID allocation now hard-require a reachable, up-to-date Worker plus `WORKER_URL`; the previous direct-Firebase and time-based fallbacks were removed, so a missing/old Worker fully disables admin catalog editing and Mini-App booking/BiLED creation.
- **(confirmed)** Bot cart checkout of a sized product is structurally impossible (size is always `None` → `size_required`); mitigated only by blocking add-to-cart of sized products.

**Verdict**: NEEDS_CHANGES

## High-level view

The order/cancel/booking rewrite on both the Worker and Python sides is sound: each path reads a root ETag, mutates catalog stock plus a reservation/slot marker plus the order/booking record in one object, and writes with `If-Match`, retrying on 412. Reservation markers (`order_reservations`) and the `stock_reserved` column make cancel-time restock exactly-once, and idempotency is keyed on a random client key plus a normalized request fingerprint so replays are safe while a changed payload conflicts loudly.

The one place the atomicity model breaks is booking slot reconciliation. `push_all_booking_slots` was changed from additive per-day PATCH to a full-tree PUT built solely from SQLite active bookings, on the premise that SQLite is the single source of truth. But Mini-App bookings created through the Worker live only in Firebase (`bookings/b_<uid>_<key>` + `slots/<date>/b_...`) and are never imported into SQLite — `restore_orders` can't parse their non-numeric key and expects a `service` field the Worker never writes. So the full PUT deletes live slot holds on every startup and every `/firebase` run, and since bot bookings and Worker bookings live in different slot-key namespaces, only the SQLite ones survive.

The capability gating is correct as designed but tightens deployment coupling hard. With rules now `.write: false` on catalog, counters, orders, bookings, and biled_orders, the browser has exactly one write path: the signed Worker. `ensureWorkerFeature`/`workerFeatures` fail-open on network error (good) but fail-closed when the Worker is reachable and old, and the old time-based counter fallback was deleted. This is the intended security posture, but it means an unset `WORKER_URL` or a stale Worker silently removes the admin's ability to manage the catalog and the customer's ability to book or order BiLED.

Remaining issues are lower-severity: a sized-product cart dead end, dead legacy handlers left in both files, a client idempotency key that can lock a customer out after a hard failure, and a couple of validator branches and URL-scheme mismatches that can't be reached or only bite edge inputs.

### Booking slot reconciliation deletes Worker-owned slots

`push_all_booking_slots` (services/sync.py:832-862) was changed from additive per-day PATCH to a single full-tree PUT:

```python
by_day = {}
for row in await q.get_active_bookings():        # SQLite only
    by_day.setdefault(str(row["date"]), {})[str(row["id"])] = _slot_payload(row)
await _write(SLOTS_ROOT, by_day, method="put")   # replaces the ENTIRE slots tree
```

The stated intent is "SQLite active bookings are the single source of truth; clear stale garbage." But Mini-App bookings created through the Worker are never in SQLite. The Worker writes `bookings/b_<uid>_<clientKey>` with no numeric `id` and `slots/<date>/b_<uid>_<clientKey>` (cloudflare-worker.js `handleBooking`). The only importer, `restore_orders` (services/sync.py:1248-1272), can't adopt them for two independent reasons:

- `booking_id = _order_id(item.get("id"), key)` and `_order_id` (services/sync.py:1159-1163) does `int(value if value is not None else key)`; the key `b_12345_abc...` isn't an integer, so it returns `None` and the row is skipped.
- Even if the id parsed, the loop resolves the service via `ensure_service(item.get("service"))`, but the Worker record carries `service_id`/`service_name`, not `service` — so it would still be dropped as "xizmat/sana yo'q".

Both `initial_sync` (services/sync.py:1544) and the admin `/firebase` command (handlers/admin.py:584) run `restore_orders()` immediately before `push_all_booking_slots()`, so ordering doesn't help: the Worker bookings are never adopted, the full PUT rebuilds `slots` from SQLite rows only, and every `b_...` slot key is deleted. The `bookings/b_...` records survive (PUT targets `slots`), but their slot hold is gone, so the Mini App shows those times free and the Worker's own clash check (which reads `slots/<date>`) no longer sees them — a second customer can book the same interval. Bot bookings use the integer booking id as the slot key, a different namespace, so only they survive the rewrite. This is a behavioral regression versus the base branch, where per-day PATCH never removed keys. Fix requires adopting Worker bookings into SQLite (handle `b_` keys and the `service_name` field) before the PUT, or reconciling `slots` without replacing the whole tree.

### Capability gating removes all fallbacks when the Worker is the only writer

`database.rules.json` now sets `.write:false` on `catalog/$table/$row`, `slots/$day/$key`, `bookings/$key`, `biled_orders/$key`, `pending_orders` status fields, and all three `*_counter/n` nodes (also `.read:false` on counters). The service-account Worker bypasses rules, so the intended single write path is the signed Worker; `fb.js` enforces the same by routing catalog `put/patch/remove` through `secureCatalogWrite` and throwing `blockedWriteError` for any other protected path, including `push` (fb.js:202-235). The gating logic itself fails open on network error and fails closed only when the Worker responds without the feature flag.

The concern is the removal of every degraded-mode fallback:

- `nextId` (fb.js:239-270) previously read the counter directly and, on rule denial, fell back to a time-based id; `nextBannerId` had its own time-based fallback. Both now call `secureCatalogWrite("allocate")` with no fallback, so product/story/banner creation fails hard without a current Worker.
- `admin-shop.js` order-status changes dropped the direct-Firebase second path entirely (docs/js/admin-shop.js:828+). A missing `WORKER_URL` now yields "Holatni o'zgartirish uchun Worker kerak" instead of a mirror write.

The hardening is defensible (mirror-only writes were genuinely unsafe), but it converts the Worker from an optional accelerator into a hard dependency for admin catalog management and Mini-App booking/BiLED. Deployments must set `WORKER_URL` and deploy the ≥1.8.0 Worker before/with this change, or those flows stop working with no local fallback.

### Idempotency key lifecycle on the client

The client attempt key (app.js `currentOrderAttemptKey`/`clearOrderAttemptKey`, offline.js `attemptFor`) is a random per-checkout value persisted in `sessionStorage`, cleared only after a confirmed response. For bookings and BiLED the key is re-bound whenever the payload hash changes, so editing the selection produces a new key. For orders, though, the key is content-independent and only regenerated when null. If a first attempt leaves a non-`failed` claim (a `processing` claim after a mid-flight network drop, before `commitOrder`), and the customer then edits the cart and retries, the Worker sees a live claim with a different `request_hash` and returns `idempotency_conflict` — with no client path to reset the key short of a successful order. Same-payload retries recover fine; the gap is edit-after-hard-failure.

### Sized-product dead end in the bot cart

`get_cart` now selects `product_type`/`sizes`, and `create_order` builds `wanted` with `size=None` for every row. `_reserve_product_stock` returns a `size_required` problem for any product that has sizes, so a sized product in a bot cart can never check out. This is contained by `shop.py:add_to_cart` and `cart.py:cart_plus` rejecting add-to-cart for sized products, but the residual risk is a product already sitting in a cart when it gains sizes, or another add-to-cart path — those carts are stuck until cleared.

### Verified sound (no changes needed)

The atomic paths the review was asked to scrutinize check out. `handleOrder`/`commitOrder` claim `pending_orders/<uid>_<clientKey>` via a `null_etag` create, then decrement per-product and per-size stock, write the `order_reservations/<key>` marker, and finalize the record in one root PUT; the marker is written only in the finalizing PUT, giving an exactly-once replay signal, and stock failure sets `failed`/`reservation_state:failed`, the only state a differing payload may re-bind onto. `cancelOrderAtomic`/`cancelBookingAtomic` and Python's `compare_and_set_status` gate restock behind a conditional status update and touch only `stock_reserved = 1` rows, so mirror rows (`stock_reserved = 0`) don't inflate stock and a second cancel can't double-restock. `import_external_order` reserves only for non-cancelled resolvable rows and records the true reservation result; `restore_shop_order` links `product_id` only when it still exists and writes `stock_reserved=0`, now with header+items in one transaction and header-without-items repaired on a later run. `add_booking` validates service, `available_dates()`, and `free_slots` overlap inside one transaction with the unique `idx_bookings_slot` index (rebuilt in a savepoint, scoped to `('new','confirmed')`) as backstop, and the Worker `handleBooking` rejects non-existent calendar dates the old regex allowed.
